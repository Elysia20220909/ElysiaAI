# Ubuntu Agent Policy Lab

Ubuntu / WSL2 上で、学習する提案器と固定の許可判定を分離して試す研究用実験です。
Python 標準ライブラリだけを使い、追加パッケージ、モデルのダウンロード、常駐サービスは不要です。

## 二つの実験

`lab.py` は次を別々に検証します。

- オフラインの予算提案：合成の学習データ5件から線形回帰を学習し、未使用の入力6件にメモリ予算を提案します。固定16ページの方式と、完了可能な件数・提案量を比較します。許可判定は学習せず、最大16ページ、指定ツール・context、network=0を要求します。これはシミュレーションであり、OSの実測メモリ使用量ではありません。
- Linux の資源制御：自作の既知のワーカーを別プロセスで起動し、実行前に RLIMIT_AS=128 MiB、RLIMIT_CPU=1秒、core=0、FD=32を設定します。正常終了、256 MiBの割り当て拒否、無限ループのSIGKILL、異常終了を試験します。各故障の後に新しい正常ワーカーを起動し、親が処理を継続できることを確認します。壁時計4秒での停止はCPU上限試験の合格にはしません。

モデルの提案値は Linux ワーカーの制限値へ自動適用しません。今回の実行制限は信頼済みの固定値です。提案の誤りを検査できる段階に留め、モデルに実行や権限の変更を許可しません。

アドレス空間128 MiBはPythonランタイムも含むLinux側の上限です。提案の16ページや native-os の arena 上限と同じ単位の制約として比較しないでください。

## 実行

Linux 内でこのディレクトリへ移動して実行します。

```sh
python3 -m unittest -v
python3 lab.py
```

結果は ignored の `out/results.json` に保存します。再実行でこの結果ファイルを上書きします。
Python / カーネル / OSの版、実行日時、実験コードのSHA-256、学習データ、各評価結果を含みます。
`passed` はLinuxワーカー試験の合否です。モデルの全件成功や安全性証明を意味しません。

Windowsからは `wsl -d Ubuntu --exec ...` で明示的に実行します。
検証終了後、起動前に停止していたUbuntuを `wsl --terminate Ubuntu` で戻します。
他のディストリビューションを終了する必要はありません。

## 先行研究との関係

- [UT Austin LDOS](https://ldos.utexas.edu/) は機械学習を用いたOSの効率・性能向上を研究しています。本実験は、資源ポリシーを学習データから提案し、固定方式と比較するという研究の進め方を参考にしています。LDOSの再現実装ではありません。
- [seL4](https://sel4.systems/About/) は形式検証を重視するマイクロカーネルです。本実験では、学習する部分と許可を決める部分の責務を分けます。seL4の証明を継承するものではなく、ElysiaAIに形式的な安全性証明はまだありません。

## 境界と次の課題

このコードはホストLinux上の研究環境です。ElysiaAI独自カーネル、LLM、RAG、GPU/NPU/CXL/QPUの実装ではありません。
RLIMITは資源制限であり、ファイル・ネットワークのアクセス隔離ではありません。既知の自作ワーカー専用であり、未知のコードやモデルを実行してはいけません。
試験用プロセスは個人ファイルを読み取らず、外部通信するコードもありませんが、OSの権限としてアクセス不能にするsandboxは構築していません。

`qemu_traces.py` で native-os のQEMUログから資源トレースを抽出し、学習用と評価用をシナリオ単位で分ける段階を追加しました。結果と制約は下記のとおりです。
今後、その評価で改善が確かめられた提案だけを、Rust側のAgent契約に照合する段階へ進めます。
Linux側のCPU制限とnative-osのtick制限は別々に評価し、片方の合格をもう片方の根拠にしません。

## QEMUの実測履歴による評価

```sh
python3 -m unittest -v
python3 qemu_traces.py
```

既存の `native-os/out/agent-runtime-results.json` と各ケースの `serial.log`、`esp/EFI/BOOT/BOOTX64.EFI` を読み取ります。試験結果の失敗、重複、ローダーのハッシュ不一致、メモリ履歴の欠落・改変、回収後の空きフレーム数不一致を拒否します。既存のQEMU判定器の identity / arena 検査も再利用しています。外部リポジトリや追加依存は取得しません。

取り出す指標は arena のページ数の履歴と最大値、所有フレーム数の最大値、資源回収、CPU上限停止時のticksです。CPU時間の平均値、物理ホストのRSS、処理に必要な最小メモリはこのログから推定しません。停止ticksがない場合は不明としてnullを記録します。

元のログはQEMU上で実際に動かした試験プログラムの測定値です。入力・動作は試験用であり、一般ユーザーの作業や実用LLMの負荷を測ったものではありません。

学習側は通常推論の `infer-approve / short / deny / replay / timeout` の5シナリオ、評価側は `infer-fault / mem-budget / mem-release` の3シナリオに固定しています。同じシナリオ内のイベントを両側へ分配しません。今回は入力サイズがほぼ固定のため、前の合成データ向け線形回帰を無理に適用せず、学習側で観測した最大値を提案する単純なデータ依存方式を比較対象にします。モデルの選択や調整に評価側のページ数を使いません。

| 方式 | 提案予算 | 評価側の観測最大値を収めた件数 |
| --- | --- | --- |
| 固定上限 | 16ページ | 3 / 3 |
| 学習側の観測最大値 | 2ページ | 1 / 3 |

故障試験の観測最大値は2ページ、CPU上限試験と繰り返し確保試験は16ページでした。2ページ方式は後者で各14ページ不足します。今回の結果から予算縮小は採用しません。予算内に収まった故障試験も、タスク成功と数えたわけではありません。観測最大値の充足だけを評価しています。

8シナリオの履歴、分割、評価結果とログのコピーを `out/qemu-traces/` に保存します。抽出元report、各serialログ、ローダーのSHA-256を記録します。再実行でこの出力を上書きします。元reportにはserialログのハッシュがないため、今回付けたハッシュは抽出時点のコピーを識別するものです。実行当時からログが不変だったことを暗号学的に証明するものではありません。今回QEMUを再実行して終了コードやディスクの完全性を再検査してはいません。

次の検証では、入力やモデルの大きさが異なる負荷を追加し、予測に使える起動前の特徴量を記録します。未知の負荷では保守的な上限を維持する方式と比較し、同じ評価データを繰り返し調整に使わないよう、新しい評価用シナリオを確保します。

2026-09-24、WindowsとUbuntu 26.04.1 LTSの両方で研究フォルダーの8単体試験と実ログ8シナリオの抽出が合格しました。ページ数・フレーム数の改変、回収記録の欠落、CPU停止ticksの改変、学習／評価の混在を検査しています。途中でWindowsのCRLFを保持したログがCPU履歴検査に失敗したため、原本のbytesとハッシュは維持し、解析時だけ改行を正規化しました。LF/CRLFの両形式を試験しています。Ruffと差分検査も合格しています。

## 学習範囲外で固定上限へ戻す評価

`guarded_policy.py` は、起動モード・kernel SHA-256・推論ELF SHA-256の完全一致を適用範囲として使います。同じ識別情報の学習観測があれば、その最大値を提案候補にします。一致しない負荷、壊れた特徴量、上限を超えるモデル値では16ページへ戻します。これは信頼済みの試験設定に対する厳しい一致判定です。意味を理解した未知負荷検出や、新しい入力サイズへの汎化モデルではありません。

今回は各モードの入力がカーネルに固定されています。任意入力を導入する場合、この識別情報だけでは不十分です。入力サイズやモデル構成などを起動前に記録し、別途評価する必要があります。同一モードで将来も使用量が同じという保証もないため、全提案に `apply=false` を付け、カーネルには自動適用しません。

収集前に学習用を `infer-approve / infer-short`、評価用を `infer-model / infer-oversized / infer-mem-grow / infer-mem-limit` に固定しました。評価4ケースは前回の予算比較では未使用です。ただし既存のカーネル回帰試験で挙動が知られているため、盲検の汎化能力試験とは扱いません。

QEMUの起動直前に `prelaunch.json` を保存し、実行直後のserialファイルのSHA-256を結果レコードに記録するよう `boot_test.py` を拡張しました。評価器は起動情報、reportの識別情報、ローダーとserialのハッシュ、記録された終了コード、既存のメモリ回収判定を照合します。これで後日の取り違えや変更を検出できますが、ローカルreport自体を署名した証跡ではありません。

固定した6ケースは次のコマンドで収集します。QEMUとfirmwareの版は既存のrunnerが検査します。

```powershell
python experiments/agent_policy_lab/collect_guarded.py --qemu <qemu-system-x86_64.exe> --firmware-dir <share>
python experiments/agent_policy_lab/guarded_policy.py
```

Ubuntuではこのディレクトリから `python3 -m unittest -v` と `python3 guarded_policy.py` で解析できます。UbuntuへのQEMUのインストールは必要ありません。収集結果は `native-os/out/guarded-policy-results.json`、解析は `out/guarded-policy/results.json` に保存します。収集は対象ケースの通常のログ保存先を更新します。前回の `out/qemu-traces/` のコピーは維持しますが、元の場所を使う旧reportの再解析はハッシュ不一致で拒否される場合があります。

2026-09-25に6ケースをQEMUで新しく実行し、全件合格しました。独自カーネルと推論ELFのバイナリハッシュは前回と一致しています。

| 提案方式 | 評価4ケースの観測最大値を収めた件数 |
| --- | --- |
| 固定16ページ | 4 / 4 |
| 学習側の最大値2ページを全ケースへ適用 | 2 / 4 |
| 未知の負荷では16ページへ戻す | 4 / 4 |

未知ケース4件すべてで固定上限へ戻っています。この結果は予算不足を避ける判定の確認であり、メモリ使用量や性能の改善ではありません。次の段階で入力・モデルサイズを変えた負荷を追加し、特徴量に基づく予測を比較します。

WindowsとUbuntuの研究用単体試験は各13件、既存QEMU判定器は46件合格しました。新しい試験は、未知モード・変更されたELFやカーネル・不正なモデル値での固定上限への復帰、評価ラベルを変えても提案が変わらないこと、ログ・ローダー・起動情報の変更と異常終了コードの拒否を確認します。収集CLIのimport順による起動失敗は修正し、独立プロセスからの `--help` 試験を追加しました。Ruff・差分検査・対象コードのGitleaks検査も合格しました。Ubuntuは実行後に停止状態へ戻しています。

## 入力サイズ・モデルサイズからの予算予測

`sized_inference.py` はUbuntuの独立したプロセスで、生成した整数重みと整数入力の密行列積を計算します。形状は `(batch, features, classes)` で、入力バイト数は `batch * features * 4`、重みバイト数は `classes * features * 4` です。重みは固定の規則で生成し、分類精度の評価や学習済みLLMとしての利用はしません。

```sh
python3 -m unittest -v
python3 sized_inference.py
```

Python標準ライブラリのみを使います。各ワーカーの上限はアドレス空間128 MiB、CPU時間5秒、壁時計15秒です。12形状を各3回、計36プロセスで動かします。入力や重みを含むこの計算の開始前にtracemallocを有効にし、終了までの追跡対象の割り当てピークを測ります。Pythonランタイム全体の最大RSSも別に記録します。RSSはLinuxのru_maxrssでKiB単位です。

予測対象はtracemallocのピークであり、全RSSやRLIMIT_ASの値ではありません。256 KiBの固定比較予算と、native-osの16ページarena上限も別物です。低い予算を強制して再実行する段階は含みません。

実行前に分割と補正方式を固定しています。

| 用途 | 形状 |
| --- | --- |
| 学習 | (1,64,4), (4,64,4), (1,128,8), (4,128,8), (1,256,16), (4,256,16) |
| 補正 | (2,96,6), (3,192,12) |
| 評価 | (2,64,4), (3,128,8), (2,256,16), (8,512,32) |

学習は、入力KiB・重みKiB・定数項による線形回帰です。各形状の3回の最大観測値を使います。補正用データの正の残差の最大値に4 KiBを足し、予測値に加えてページ単位へ切り上げます。これは経験的な余裕であり、統計的な保証や最悪時の証明ではありません。

評価処理を起動する前に、モデルと全評価形状への提案を `out/sized-inference/frozen-model.json` へ保存します。学習時の各次元の範囲を超える形状は固定256 KiBへ戻します。範囲内でも未知の組み合わせはあり、誤差が出る可能性は残ります。すべて `apply=false` の提案です。

2026-09-25、Ubuntu 26.04.1 LTS / Python 3.14.4で36プロセスの測定が完了しました。

| 評価形状 | 実測の追跡メモリ最大値（bytes） | 提案予算（bytes） | 判定 |
| --- | ---: | ---: | --- |
| (2,64,4) | 2,368 | 8,192 | 観測値を充足 |
| (3,128,8) | 6,672 | 12,288 | 観測値を充足 |
| (2,256,16) | 20,180 | 24,576 | 観測値を充足 |
| (8,512,32) | 85,644 | 262,144 | 範囲外のため固定予算へ復帰 |

固定256 KiBも4件すべてを収めました。上の値はPythonの版やアロケータに依存する観測結果で、異なる実行環境への保証ではありません。最初の3件で小さな予算を提案できても、実際に使用メモリが削減されたわけではありません。CPU時間はtracemallocの計測負荷を含むため、推論性能の比較指標には使いません。

各試行のピーク、checksum、CPU時間、最大RSS、コードのSHA-256、環境情報を `out/sized-inference/results.json` に保存します。`completed` は測定の完了を示し、予算の充足は各評価行の `covered` で確認します。実行失敗は `error` と未完了の結果に残し、成功へ置き換えません。再実行では同じ出力ファイルを上書きします。

研究フォルダーの単体試験はWindows・Ubuntuで各19件合格しました。小さい行列の既知の答え、入力制限、回帰計算、学習・補正・評価の分離、範囲外での固定予算への復帰、反復時の出力一致を確認しています。


## 独自カーネル側の予算強制との接続

これは予測の自動適用に先立つ、起動予算の強制と回収の検証です。Pythonのtracemalloc値をnativeのページ数へ変換した結果ではありません。
[検証内容と再現コマンド](../../docs/native-os/INFERENCE_MEMORY_VALIDATION.md#agent-の縮小予算を実際に強制する試験)を参照してください。

## nativeのサイズ別ページ予測

`native_sized.py` は、専用のRing 3 ELFで12形状の整数行列積を各2回計算し、カーネルの割り当てログからページ数を収集します。
学習6形状・補正2形状で予測を作り、評価4形状の測定前にモデルを保存します。解析はWindows・Ubuntuの両方で動きます。

2026-09-25の24起動は合格し、評価の実測は2/5/10/13ページ、提案は4/7/12/16ページでした。
今回の固定メモリ配置ではサイズからの解析式が全件で実測と一致し、回帰の優位性は確認していません。
予測対象はnative arenaの割り当てページ数で、Pythonの追跡対象メモリとは別です。提案は自動適用しません。

[実装・分割・結果・再現手順](../../docs/native-os/SIZED_INFERENCE_VALIDATION.md)を参照してください。
保存先は `out/native-sized-20260925/`。新しく収集するときは `--collect --run-dir <新規ディレクトリ>` とQEMU・firmwareのパスを指定します。
既存の記録は `python3 native_sized.py --run-dir out/native-sized-20260925` で再解析できます。
