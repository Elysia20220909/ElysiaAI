# Ubuntu Agent Policy Lab

Ubuntu / WSL2 上で、学習する提案器と固定の許可判定を分離して試す研究用実験です。
Python 標準ライブラリだけを使い、追加パッケージ、モデルのダウンロード、常駐サービスは不要です。

## 二つの実験

`lab.py` は次を別々に検証します。

- オフラインの予算提案：合成の学習データ5件から線形回帰を学習し、未使用の入力6件にメモリ予算を提案します。固定16ページの方式と、完了可能な件数・提案量を比較します。許可判定は学習せず、最大16ページ、指定ツール・context、network=0を要求します。これはシミュレーションであり、OSの実測メモリ使用量ではありません。
- Linux の資源制御：自作の既知のワーカーを別プロセスで起動し、実行前に RLIMIT_AS=128 MiB、RLIMIT_CPU=1秒、core=0、FD=32を設定します。正常終了、256 MiBの割り当て拒否、無限ループのSIGKILL、異常終了を試験します。各故障の後に新しい正常ワーカーを起動し、親が処理を継続できることを確認します。壁時計4秒での停止はCPU上限試験の合格にはしません。

モデルの提案値は Linux ワーカーの制限値へ自動適用しません。今回の実行制限は信頼済みの固定値です。提案の誤りを検査できる段階に留め、モデルに実行や権限の変更を許可しません。

アドレス空間128 MiBはPythonランタイムも含むLinux側の上限です。提案の16ページや native-os の arena 上限と同じ単位の制約として比較しないでください。

## 実行

Linux 内でこのディレクトリへ移動して実行します。

```sh
python3 -m unittest -v
python3 lab.py
```

結果は ignored の `out/results.json` に保存します。再実行でこの結果ファイルを上書きします。
Python / カーネル / OSの版、実行日時、実験コードのSHA-256、学習データ、各評価結果を含みます。
`passed` はLinuxワーカー試験の合否です。モデルの全件成功や安全性証明を意味しません。

Windowsからは `wsl -d Ubuntu --exec ...` で明示的に実行します。
検証終了後、起動前に停止していたUbuntuを `wsl --terminate Ubuntu` で戻します。
他のディストリビューションを終了する必要はありません。

## 今回の観測

2026-09-24、Ubuntu 26.04.1 LTS、Python 3.14.4、WSL2カーネル
6.18.33.2-microsoft-standard-WSL2で実行しました。

| 対象 | 結果 |
| --- | --- |
| 許可判定・学習評価の単体試験 | 5件合格 |
| Linuxワーカー試験 | 7件合格。正常4回、メモリ拒否・CPU上限停止・異常終了各1回 |
| 固定16ページ | 合成評価で6件中5件完了可能、要求合計96ページ |
| 学習した予算 | 合成評価で6件中5件完了可能、要求合計51ページ。17ページの提案を拒否 |

51ページには拒否された17ページも含みます。どちらの合計も実際の割り当て量ではありません。
必要量20ページの分布変化ケースは両方式で失敗します。この失敗を合格や改善に置き換えません。
少数の合成データに適した線形モデルなので、実運用での効率改善やモデル一般の優秀さは示しません。

## 先行研究との関係

- [UT Austin LDOS](https://ldos.utexas.edu/) は機械学習を用いたOSの効率・性能向上を研究しています。本実験は、資源ポリシーを学習データから提案し、固定方式と比較するという研究の進め方を参考にしています。LDOSの再現実装ではありません。
- [seL4](https://sel4.systems/About/) は形式検証を重視するマイクロカーネルです。本実験では、学習する部分と許可を決める部分の責務を分けます。seL4の証明を継承するものではなく、ElysiaAIに形式的な安全性証明はまだありません。

## 境界と次の課題

このコードはホストLinux上の研究環境です。ElysiaAI独自カーネル、LLM、RAG、GPU/NPU/CXL/QPUの実装ではありません。
RLIMITは資源制限であり、ファイル・ネットワークのアクセス隔離ではありません。既知の自作ワーカー専用であり、未知のコードやモデルを実行してはいけません。
試験用プロセスは個人ファイルを読み取らず、外部通信するコードもありませんが、OSの権限としてアクセス不能にするsandboxは構築していません。

`qemu_traces.py` で native-os のQEMUログから資源トレースを抽出し、学習用と評価用をシナリオ単位で分ける段階を追加しました。結果と制約は下記のとおりです。
今後、その評価で改善が確かめられた提案だけを、Rust側のAgent契約に照合する段階へ進めます。
Linux側のCPU制限とnative-osのtick制限は別々に評価し、片方の合格をもう片方の根拠にしません。

## QEMUの実測履歴による評価

```sh
python3 -m unittest -v
python3 qemu_traces.py
```

既存の `native-os/out/agent-runtime-results.json` と各ケースの `serial.log`、`esp/EFI/BOOT/BOOTX64.EFI` を読み取ります。試験結果の失敗、重複、ローダーのハッシュ不一致、メモリ履歴の欠落・改変、回収後の空きフレーム数不一致を拒否します。既存のQEMU判定器の identity / arena 検査も再利用しています。外部リポジトリや追加依存は取得しません。

取り出す指標は arena のページ数の履歴と最大値、所有フレーム数の最大値、資源回収、CPU上限停止時のticksです。CPU時間の平均値、物理ホストのRSS、処理に必要な最小メモリはこのログから推定しません。停止ticksがない場合は不明としてnullを記録します。

元のログはQEMU上で実際に動かした試験プログラムの測定値です。入力・動作は試験用であり、一般ユーザーの作業や実用LLMの負荷を測ったものではありません。

学習側は通常推論の `infer-approve / short / deny / replay / timeout` の5シナリオ、評価側は `infer-fault / mem-budget / mem-release` の3シナリオに固定しています。同じシナリオ内のイベントを両側へ分配しません。今回は入力サイズがほぼ固定のため、前の合成データ向け線形回帰を無理に適用せず、学習側で観測した最大値を提案する単純なデータ依存方式を比較対象にします。モデルの選択や調整に評価側のページ数を使いません。

| 方式 | 提案予算 | 評価側の観測最大値を収めた件数 |
| --- | --- | --- |
| 固定上限 | 16ページ | 3 / 3 |
| 学習側の観測最大値 | 2ページ | 1 / 3 |

故障試験の観測最大値は2ページ、CPU上限試験と繰り返し確保試験は16ページでした。2ページ方式は後者で各14ページ不足します。今回の結果から予算縮小は採用しません。予算内に収まった故障試験も、タスク成功と数えたわけではありません。観測最大値の充足だけを評価しています。

8シナリオの履歴、分割、評価結果とログのコピーを `out/qemu-traces/` に保存します。抽出元report、各serialログ、ローダーのSHA-256を記録します。再実行でこの出力を上書きします。元reportにはserialログのハッシュがないため、今回付けたハッシュは抽出時点のコピーを識別するものです。実行当時からログが不変だったことを暗号学的に証明するものではありません。今回QEMUを再実行して終了コードやディスクの完全性を再検査してはいません。

次の検証では、入力やモデルの大きさが異なる負荷を追加し、予測に使える起動前の特徴量を記録します。未知の負荷では保守的な上限を維持する方式と比較し、同じ評価データを繰り返し調整に使わないよう、新しい評価用シナリオを確保します。

2026-09-24、WindowsとUbuntu 26.04.1 LTSの両方で研究フォルダーの8単体試験と実ログ8シナリオの抽出が合格しました。ページ数・フレーム数の改変、回収記録の欠落、CPU停止ticksの改変、学習／評価の混在を検査しています。途中でWindowsのCRLFを保持したログがCPU履歴検査に失敗したため、原本のbytesとハッシュは維持し、解析時だけ改行を正規化しました。LF/CRLFの両形式を試験しています。Ruffと差分検査も合格しています。
