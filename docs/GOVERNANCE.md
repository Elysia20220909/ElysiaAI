# プロジェクトガバナンス

## 概要

ElysiaAI はオープンソースプロジェクトです。開発はコミュニティ主導で進め、透明性のある意思決定と安全な運用を重視します。この文書では、プロジェクトの役割、意思決定プロセス、レビュー、リリース、セキュリティ対応の方針を説明します。

## プロジェクト構造

### プロジェクトオーナー

- 最終的な意思決定権限を持ちます。
- セキュリティ、インフラ、リリース方針に責任を持ちます。
- プロジェクトの方向性を定めます。

### メンテナー

- コードレビューとマージを担当します。
- Issue と Pull Request を管理します。
- リリース作業と変更履歴の管理を行います。
- 詳細は [MAINTAINERS.md](MAINTAINERS.md) を参照してください。

### 貢献者

- コード、ドキュメント、テスト、Issue 報告、機能提案などを通じて参加します。
- コミュニティでの質問対応や改善提案も重要な貢献です。
- 詳細は [CONTRIBUTORS.md](CONTRIBUTORS.md) を参照してください。

## 意思決定プロセス

### レベル 1: 日常的な変更

対象例:

- タイポ修正
- 小さなバグ修正
- 軽微なリファクタリング
- ドキュメントの補足

プロセス:

1. Pull Request を作成します。
2. 1 人以上のメンテナーがレビューします。
3. 承認後にマージします。

目安: 通常 24-48 時間。

### レベル 2: 機能追加や中規模の改善

対象例:

- 新しいエンドポイントの追加
- UI の改善
- パフォーマンス最適化
- 既存機能の拡張

プロセス:

1. Issue で提案し、方針を議論します。
2. 設計の合意後に Pull Request を作成します。
3. 2 人以上、または関係領域のメンテナーがレビューします。
4. 承認後にマージします。

目安: 通常 1 週間程度。

### レベル 3: 重大な変更

対象例:

- アーキテクチャの大きな変更
- API の破壊的変更
- セキュリティポリシーの変更
- ライセンスや運用モデルに影響する変更

プロセス:

1. Issue として RFC を作成します。
2. 少なくとも 1 週間、コミュニティとメンテナーで議論します。
3. メンテナー全員、または必要な範囲の責任者がレビューします。
4. 実装計画を承認します。
5. Pull Request を作成し、通常のレビューを行います。
6. 承認後にマージします。

目安: 通常 1 か月以上。

## RFC プロセス

大きな変更には RFC が必要です。RFC は、変更の目的、影響、代替案、未解決事項を明確にするための設計文書です。

### RFC が必要な変更

- 新しい主要機能
- API の破壊的変更
- アーキテクチャの大幅な変更
- セキュリティポリシーの変更
- ライセンスや公開方針の変更

### RFC テンプレート

```markdown
# RFC: [タイトル]

## 概要
[変更内容の簡潔な説明]

## 動機
[なぜこの変更が必要か]

## 詳細設計
[技術的な詳細]

## 代替案
[検討した他のアプローチ]

## 未解決事項
[まだ決まっていないこと]

## 影響
- 既存機能への影響
- パフォーマンスへの影響
- セキュリティへの影響
- 互換性への影響
```

### RFC のライフサイクル

1. **提案**: Issue として作成します。
2. **議論**: コミュニティとメンテナーからフィードバックを集めます。
3. **修正**: 必要に応じて RFC を更新します。
4. **判断**: メンテナーが承認、却下、または保留を決定します。
5. **実装**: 承認された場合は Pull Request を作成します。

## リリースプロセス

### バージョニング

[Semantic Versioning 2.0.0](https://semver.org/) に従います。

- **MAJOR**: 破壊的変更
- **MINOR**: 後方互換性のある機能追加
- **PATCH**: 後方互換性のあるバグ修正

### リリーススケジュール

- **PATCH**: 必要に応じて随時
- **MINOR**: 機能追加がまとまった時点
- **MAJOR**: 破壊的変更が必要な場合

### リリース手順

1. CHANGELOG を更新します。
2. バージョン番号を更新します。
3. タグを作成します。例: `git tag v1.2.3`
4. GitHub Releases を作成します。
5. リリースノートを公開します。
6. 必要に応じてコミュニティへ通知します。

## コードレビューガイドライン

### レビュアーの責任

- [ ] 要件を満たしているか確認する
- [ ] コードスタイルに従っているか確認する
- [ ] テストが含まれているか確認する
- [ ] ドキュメントが必要に応じて更新されているか確認する
- [ ] セキュリティ上の問題がないか確認する
- [ ] パフォーマンスや互換性への影響を確認する

### レビュープロセス

1. **初回レビュー**: 可能な限り 24-48 時間以内に行います。
2. **フィードバック**: 建設的かつ具体的に伝えます。
3. **変更依頼**: 理由と期待する修正内容を明確にします。
4. **承認**: 懸念点が解消されたら承認します。

### マージ基準

- [ ] CI チェックが通過している
- [ ] 必要なレビューが完了している
- [ ] 未解決のコメントがない
- [ ] コンフリクトが解消されている
- [ ] 必要に応じて CHANGELOG が更新されている

## 行動規範と実施

[CODE_OF_CONDUCT.md](../CODE_OF_CONDUCT.md) に違反する行為が報告された場合、次の流れで対応します。

1. メンテナーへ非公開で連絡します。
2. メンテナーが事実確認を行います。
3. 状況に応じて適切な措置を決定します。
4. 報告者へ結果を通知します。

### 措置のレベル

1. **警告**: 初回または軽微な違反
2. **一時停止**: 繰り返し、または中程度の違反
3. **永久停止**: 重大、または継続的な違反

## コミュニティ参加

### 議論の場

- **GitHub Issues**: バグ報告、機能要望、技術的な議論
- **GitHub Discussions**: 質問、アイデア、一般的な相談
- **Pull Requests**: コードレビューと実装議論

## セキュリティ

セキュリティ脆弱性の報告方法は [SECURITY.md](SECURITY.md) を参照してください。

### セキュリティ開示プロセス

1. 脆弱性を非公開で報告します。
2. メンテナーが内容を確認します。
3. 修正を開発し、必要なテストを行います。
4. セキュリティアップデートをリリースします。
5. 修正リリース後に公開開示します。
