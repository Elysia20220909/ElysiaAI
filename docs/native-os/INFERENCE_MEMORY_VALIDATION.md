# M6b: 推論用メモリの拡張と上限管理

推論プロセスが、固定の4 KiBデータページに加えて、最大64 KiBの専用作業領域を増減できるようにする。
上限はカーネルの信頼済み起動定義に置き、ELFやシステムコールの引数から増やせない。
現在の整数分類器も、この領域にモデルと入力を置いて計算する。

## 権限と予算

| 対象 | 作業領域の上限 | 所有フレームの上限 | 累積 tick 上限 |
| --- | --- | --- | --- |
| `INFERENCE_BOOT` の PID 0 | 16ページ / 64 KiB | 32 | 1024 |
| 通常の `BOOT` の PID 0 | 0 | 32 | 1024 |
| PID 1 の資料サービス | 0 | 32 | 64 |

`launch::Definition.memory_pages` は0〜16ページの範囲で削減できる。サービスへの付与や、
カーネルの `CEILING` を超える値は起動定義の検査で拒否する。初回と復旧で同じ定義を使う。

所有フレームはデータだけでなく、rootと中間ページテーブルも数える。
固定した QEMU 構成では、通常のプロセスは14、推論プロセスは空の作業領域用テーブル込みで15フレームを使う。
16ページまで拡張した推論プロセスは31フレーム。作業領域を0に戻しても、終了するまではテーブルの1フレームを保持する。
この数値は今回の固定配置での値であり、一般的なOSのメモリ使用量ではない。

## 暫定 ABI

`int 0x80`、RAX=9、RDI=確保後に必要なページ数。単位は4 KiB。
領域は `0x90000000` から連続する仮想アドレスで、物理フレームは連続する必要がない。
権限はプロセス専用の user/RW/NX。実行は禁止する。

| 結果 | RAX | 既存領域の扱い |
| --- | --- | --- |
| 1〜上限ページへ変更 | `0x90000000` | 残る部分のデータを維持し、新しいページはゼロ |
| 0ページへ変更 | 0 | 全データページを外し、消去して返却 |
| 権限なし | −13 / EACCES | 変更なし。0ページ要求も拒否 |
| ページ上限超過 | −22 / EINVAL | 変更なし |
| フレーム予算・物理フレーム不足 | −12 / ENOMEM | 今回の追加分だけを消去・返却し、以前の領域を維持 |

同じページ数への要求は追加確保をしない。領域の縮小は末尾から行う。
解放済みポインターを継続して使うことはできない。再確保で同じ仮想アドレスを使う場合も内容はゼロにする。
`log` や IPC のバッファ検査は、現在割り当て済みの範囲内であればページ境界をまたぐコピーを許可する。
既存のコピー長上限（logは128 bytes、IPCは64 bytes）と固定ページの検査は維持する。

## 変更と回収の順序

1. 呼び出し元をカーネルの CR3 に移し、ユーザー側の古いTLB対応を失効させる。
2. 拡張時は必要なフレームをすべて確保・ゼロ化してから、ユーザーの葉エントリーへ反映する。
   途中で失敗した場合は新しい対応を公開せず、追加分だけを返す。
3. 縮小時は対応を外してから、物理ページを消去し、フレーム管理へ返す。
4. ユーザーへ戻る際に CR3 を再ロードする。終了・故障・tick上限時は領域とテーブルを通常の所有資源として回収する。

前提は1 CPU、カーネル内の割り込み無効、PCIDを使わない構成、global指定のないユーザーページ。
マルチコア向けのTLB同期は含まない。待機中の受信プロセスが領域を変更することもない。

## 推論との接続

M6a の24-byteモデルと8-byte入力を2ページの作業領域へコピーし、整数計算する。
デコードと予測の結果は領域を参照しない値で受け取り、通常は提案前に全解放する。
既存の `infer-budget` / `infer-fault` は2ページを保持したまま暴走・故障させる。
承認、資料権限、操作の一度だけの実行、永続記録の契約は変更しない。

## QEMU の追加ケース

| ケース | 検査 |
| --- | --- |
| `infer-mem-grow` | 2→16→1→16ページ。元データ維持と新規ゼロ、ページをまたぐコピー、縮小後の範囲拒否 |
| `infer-mem-limit` | 16ページを保持し、17と `u64::MAX` を拒否。既存データとフレーム数の不変 |
| `infer-mem-release` | 確保・書き込み・縮小・再拡張・全解放を8回。全ページのゼロと残るデータの維持 |
| `infer-mem-fault` | 16ページに書き込んだ状態で #UD。停止後に全資源を回収 |
| `infer-mem-budget` | 16ページを保持して無限ループ。累積1024 ticksで停止し回収 |
| `infer-mem-rollback` | 作成時15境界、1→16ページ拡張時15境界へフレーム予算不足を注入。残るデータ・対応・空き数の不変 |
| `infer-mem-guard` | 領域末尾の次のページを読み、Ring 3 #PF / error=4 / CR2=`0x90010000` |
| `infer-mem-nx` | 領域内の命令を実行し、#PF / error=0x15 / CR2=`0x90000000` |
| `infer-mem-released` | 全解放後に読み、#PF / error=4 / CR2=`0x90000000` |

各ケースは、資料サービスへの確保要求がEACCES、領域ポインターのコピーがEFAULTとなることも検査する。
サービスが相手切断後に正常終了し、双方のフレーム数が起動前の基準値へ戻ることを要求する。
操作は Empty、実行0回、試験用ディスク全体は不変でなければならない。

ホスト判定器は、各要求の戻り値、割り当て数と総フレーム数、停止理由、回収順序を照合する。
欠落した回収、誤った上限、上限拒否時のページ数変化、停止後の再実行、別の例外を合格にしない。
既存12件の推論試験にもこの検査を適用する。

```powershell
python native-os/tools/boot_test.py --case infer-mem-release --qemu <qemu-system-x86_64.exe> --firmware-dir <share>
python native-os/tools/boot_test.py --case all --qemu <qemu-system-x86_64.exe> --firmware-dir <share>
```

## 確認範囲

2026-09-23、Windowsホスト上の固定した QEMU 11.1.0 / q35 / TCG / 1 CPU / 256 MiB と Rust 1.96.0で検証した。

| 検証 | 結果 |
| --- | --- |
| Rust単体試験 | 72件合格 |
| Python判定器試験 | 45件合格。即時受信と待機後の受信、プロセス間の異なる実行順序も検査 |
| QEMU | 初回90件中80件合格。判定器の順序依存を修正後、影響する推論21件とIPC 1件を再実行し22件すべて合格 |
| 静的解析 | ホスト・ゲスト・UEFIローダーのClippy（警告をエラー化）、Rustfmt、変更したPythonのRuffが合格 |
| 生成コード | 推論クライアントのbin/libアセンブリにx87/SIMD命令なし。ELFはRX 4072 bytes、RW 928 bytesで各4 KiB以内 |

初回の10件の不合格は、IPCの容量不足を即時結果だけで判定したことと、
新しい判定器でサービスの拒否処理が常に推論より先に走ると仮定したことによる。
実際の即時・待機後の両経路を確認し、プロセスごとの要求順と生存期間を照合するよう修正した。
欠落・重複・不正な待機解除・停止後の処理を拒否する単体試験も追加した。

合格範囲は初回と再試験を合わせた全90ケースであり、修正後に全90件をもう一度実行した記録ではない。
両実行のカーネルと4つのユーザーELF、QEMU、ファームウェアのハッシュは一致する。
`out/regression-initial.json` に初回、`out/regression-recheck.json` に再試験、
`out/validation-summary.json` にケースごとの根拠を残す。元の失敗ログは上書きして合格に変えない。
ログ、ELFとソースのハッシュ、専用ディスクは ignored の `native-os/out/` に残す。

確保途中の失敗は、実際のカーネル確保経路でフレーム予算を削減して注入した。
仮想マシン全体のRAMを消費し尽くす試験、複数推論プロセスの同時実行、承認待ち中の新しい故障注入は行っていない。
資料サービスから割り当て済み領域へ直接ロードする新規試験も含まず、今回の相手側検査はシステムコール境界で行う。

64 KiBはこの段階の作業領域であり、実用LLMを動かせる容量としては扱わない。
汎用ヒープ、任意アドレスへのmmap、共有メモリ、スワップ、学習済みモデルのロード、FPU/SIMD、GPU、実機対応は未実装。
ELFのRX/RWセグメント各4 KiBと4 KiBスタックの制限も維持する。


## Agent の縮小予算を実際に強制する試験

2026-09-25、既存の `ReadAgent` の起動上限を使い、同じ推論ELFを異なるarena予算で動かす2ケースを追加した。
Agentへのバインドとプロセス構築が同じ検証済みmanifestから起動設定を得る。
信頼済みの起動モード73/74が予算を選び、ユーザープロセスには従来の承認用モード56を渡す。
推論と資料サービスのELFには変更を加えず、入力も通常の承認ケースと同じに保つ。

| ケース | 推論arena上限 | QEMUで確認した結果 |
| --- | ---: | --- |
| `infer-quota-approve` | 2ページ / 8 KiB | 2ページ確保、推論、全解放、試験runnerによる承認後に1回実行。再起動時は記録を読み、権限を復元せず再実行しない |
| `infer-quota-denied` | 1ページ / 4 KiB | 2ページ要求をEINVALで拒否。確保0ページを維持し、クライアントはstatus=1で終了。操作はEmpty、実行0回、journalディスクは不変 |

両ケースともサービスへのarena権限は0のままで、両プロセス終了後の空きフレーム数は起動前の基準値へ戻った。
成功ケースの承認は自動試験入力であり、人間による操作試験を実施したことは意味しない。
縮小するのは推論作業領域だけであり、ELF、スタック、ページテーブルなどを含むプロセス全体のメモリではない。
元の上限16ページでもこの推論の使用量は2ページなので、今回の結果を実使用メモリの削減とは扱わない。

```powershell
python native-os/tools/boot_test.py --case infer-quota-approve --qemu <qemu-system-x86_64.exe> --firmware-dir <share>
python native-os/tools/boot_test.py --case infer-quota-denied --qemu <qemu-system-x86_64.exe> --firmware-dir <share>
```

追加2ケースと `infer-approve / infer-replay / infer-mem-fault / infer-mem-budget` の計6ケースを、
Windows上のQEMUで実行し、全件合格した。回帰試験全体92ケースの再実行ではない。
今回の記録はローカルの `native-os/out/quota-results.json`、ケース別serialログ、起動前の識別情報に残した。
Rustのライブラリ試験79件、Python判定器47件、研究用試験19件も合格した。
判定器の新しい負例は、上限の水増し、拒否時のページ増加、異常終了の成功扱い、拒否後の推論結果を検出する。

Ubuntu側の `sized_inference.py` はPythonの追跡対象メモリを予測する実験であり、今回の2/1ページは
nativeの固定推論に対する試験予算である。Ubuntuの回帰モデルからの自動変換・適用は実装していない。
次はnative側でも入力・モデルサイズを変えてarenaのピークを収集し、その単位で評価した提案を
この起動上限に渡す。サイズの異なる推論の移植、未知負荷の扱い、予算不足時の再計画は今後の課題となる。
