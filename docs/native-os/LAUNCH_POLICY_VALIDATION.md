# M3g：起動定義と最小権限

起動時の ELF・通信先・資料権限・資源上限を `launch::Definition` にまとめた。
`BOOT` はカーネル内の信頼済み定義、`CEILING` は許可の上限である。
定義を増やすだけで任意の ELF や通信先を許可する仕組みではない。

## 適用範囲

現在の2プロセスと埋め込み ELF を対象にする。クライアントは PID 0、サービスは PID 1。
クライアントは資料0の読み取り権限を省略できる。サービスには資料権限を許可しない。
通信先は相互の1プロセスに限り、別 PID、同一 PID、別役の ELF を拒否する。
送受信ハンドルは既存 Channel の所有者・操作検査を通す。ELF 自体は権限を発行できない。

| 定義 | クライアント | サービス |
| --- | --- | --- |
| ELF | Client | Service |
| 通信先 | PID 1 | PID 0 |
| 資料 | 資料0、または権限なし | 権限なし |
| 所有フレーム上限 | 最大32 | 最大32 |
| CPU tick 上限 | 最大1024 | 最大64 |

フレーム数はページテーブルを含み、既存 allocator の上限として適用する。
ゼロや上限超過は拒否する。必要数未満の有効な上限では確保が失敗し、部分確保を回収する。
CPU 上限は Process に保持し、タイマー割込み時に適用する。厳密な経過時間の課金ではない。
再起動でサービスの tick はリセットするが、クライアントの累積 tick は維持する。

## 初回と復旧

初回は定義ペアを検査してから権限を発行する。検証済み定義で ELF とレジスターを選び、
確保を完了したプロセスだけを公開する。資料権限を省略した場合、ハンドルを隠すだけでなく
カーネルの Grant 自体を作らない。

資料サービスは発行時の定義を保存する。復旧候補に別の定義を渡すと拒否するため、
上限内であっても再起動時だけ資料権限や資源上限を増やせない。
候補の構築失敗は生きている接続と世代を変更しない。成功時にだけ新しい空間・接続・権限を公開する。
古い権限を再使用できないこと、8回の復旧と資源回収は従来の試験を継続する。

## 検証

2026-09-13、Windows 上の固定ツール（Rust 1.96.0、QEMU 11.1.0、既存 UEFI）で検証。
追加依存・インストール処理・外部通信・Git hooks・CI 設定の変更はない。
既存の依存関係は `native-os/DEPENDENCIES.md` の確認済み環境を再利用した。

- Rust：54件（boot protocol 11、memory 7、kernel 36）。
- Python の判定器：25件。新しい証跡の削除、フレーム上限・資料権限の改変を不合格にする。
- QEMU：既存45ケースで確認。復旧6ケースに不正定義4種の拒否と、初回・各再起動の定義照合を追加。
- Rustfmt、ホストと x86_64-unknown-none の Clippy（警告をエラー扱い）、差分検査。

詳細ログとビルド結果は ignored の `native-os/out/` と `native-os/target/` に保存する。

## 限界

起動定義はコンパイル時に埋め込む。外部設定ファイル、動的 spawn、任意のプロセス数、
任意の権限委譲、実機対応は含まない。従来の M3a/M3b の攻撃用ハンドル配布は試験専用経路として残る。
権限なしのクライアント定義と上限縮小は単体試験で確認し、実際の復旧アプリは標準 BOOT 定義で検証する。
