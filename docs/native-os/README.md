# ElysiaAI // INFINITE RESONANCE — 独自 OS の構想

ElysiaAI を、自作カーネルを持つローカルファーストの AI-Native OS として育てる。
人の目的を受け取り、任された範囲で作業を進め、途中から再開できる環境を目指す。

状態: 基本設計と M1 / M2a / M2b / M2c 実装。固定した QEMU / UEFI 構成で、独自カーネルの起動、
物理ページ管理、独自ページテーブル、Ring 3 の 2 プロセス、タイマー切替と停止後の資源回収を検証した。
ユーザーの保護違反後も正常なプロセスは継続する。推論・実機動作・CPU 時間の強制制限は未検証。
実測と残る範囲は [M1](BOOT_VALIDATION.md)、[M2a](MEMORY_VALIDATION.md)、
[M2b](USERSPACE_VALIDATION.md)、[M2c](LIFECYCLE_VALIDATION.md) に記載する。

## 目指す体験

例えば、ユーザーが「昨日の開発の続きをしたい」と伝えると、選んだ作業に関係する資料、
判断、未完了の処理を取り出せる。ElysiaAI は次の操作と必要な権限を示し、
承認された範囲で実行する。ユーザーは作業を中断し、結果を確かめ、必要な記憶を消せる。

AI-Native の具体的な要件を次に置く。

- アプリとサービスが、入力、必要な権限、結果、中断条件を機械で扱える形で公開する。
- 依頼ごとに実行主体、利用できる資源、進行状態、実行結果を結び付ける。
- 作業の再開時に、完了済みの副作用と、成否が不明な処理を区別する。
- 推論プロセスを停止しても、手動操作、権限の取り消し、基本的な復旧を利用できる。
- 情報の保存、検索、外部送信をユーザーが制御できる。

これらを実際に確かめるため、最初の AI 連携は「許可した資料だけを読み、要約の下書きを返す」
という狭い用途にする。任意のシェル実行や自動的なシステム更新は、初期の対象に含めない。

## 現在のリポジトリとの関係

調査基準は 2026-09-12 に確認した `master` のコミット
[`52dfb575`](https://github.com/Elysia20220909/ElysiaAI/commit/52dfb575f8857e7e8945ace2cbe6bb31820aa7c0)。
下表はソースと設定を読んで確認した構成であり、この設計作業での実行結果ではない。

| 既存の領域 | 確認できる役割 | 独自 OS への扱い |
| --- | --- | --- |
| [Bun / Elysia サーバー](../../packages/server/package.json) | ホスト OS 上の API とアプリ基盤 | 操作契約や利用体験の参考にする。直接移植できるとは扱わない |
| [Python の構成](../../pyproject.toml) | FastAPI、推論、検索などの依存関係 | 推論サービスの設計資産として評価する |
| [既存 kernel のメモリ管理](../../kernel/memory/manager.py)、[GDT](../../kernel/arch/x86/gdt.py) | Python で固定値や構造を返す実験コード | 物理メモリ管理や CPU の保護設定を実装済みと数えない |
| [Tauri の構成](../../src-tauri/Cargo.toml) | 既存 OS を利用するデスクトップアプリ | 独自 OS のドライバーや画面基盤とは別に移植性を評価する |
| [AbyssRTOS シミュレーター](../../scripts/abyss_rtos_sim.py) | ループバックへの UDP テレメトリー送信 | ベアメタル起動、リアルタイム性、メモリ隔離の証拠にはしない |

[既存アーキテクチャ](../ARCHITECTURE.md)には、実装説明と長期構想が含まれている。
この文書群では、既存の Cognitive Kernel と新しい OS カーネルを区別する。
既存の `kernel/`、`python/`、`src-tauri/` の名前や動作は変更しない。

最初の実装は `native-os/` の独立した Cargo workspace に配置した。
既存の Tauri 用 Rust 設定を適用せず、ローダーとカーネルを別ターゲットでビルドする。
ElysiaAI // INFINITE RESONANCE をプロジェクト名として保ち、カーネル固有の名称は未決定とする。
AbyssRTOS との名称統合や、リアルタイム OS としての保証も未決定である。

## 長期的な範囲

初期の対象は、QEMU 上の一つの x86-64 構成と UEFI 起動である。
そこからプロセス隔離、権限付きの作業、ゲスト内のローカル推論、日常利用の順に広げる。

実機ドライバー、GPU 推論、既存アプリとの互換性、サスペンド、更新と復旧、日本語入力は、
それぞれ独立した設計と検証が必要になる。既存の Windows / Linux 向けバイナリが動くことは前提にしない。
完了時期は、最初の起動と隔離の実験結果を得てから見積もる。
