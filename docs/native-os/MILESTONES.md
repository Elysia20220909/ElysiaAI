# 独自 OS の段階別検証計画

状態: 段階別計画。2026-09-12 に固定した仮想環境で M1 の正常起動と故障試験を確認した。
M0 の手順を整備したが、新規マシン全体での再現は未確認。
M2a の物理ページ管理に、M2b の Ring 3・最小システムコール・協調切替を追加した。
M2c では、固定した 2 プロセスの終了・故障・tick 上限時の回収とタイマー切替を検証した。
64 世代の再生成でも空きフレーム数が戻ることを確認した。
M3a では、固定した 2 者間の IPC と権限ハンドル、待機・起床、相手終了時の回収を検証した。
M2 の一般化、M3 の権限委譲・RAM 資料サービス、M4 以降は未達成。実測は [起動検証](BOOT_VALIDATION.md)、
[メモリ検証](MEMORY_VALIDATION.md)、[ユーザー空間の検証](USERSPACE_VALIDATION.md)、
[資源回収と実行制御](LIFECYCLE_VALIDATION.md)、[通信と権限](IPC_VALIDATION.md) を参照する。
基準コミットと既存構成は[構想](README.md)、実装上の境界は[基本設計](ARCHITECTURE.md)を参照する。

## 判定の原則

合格は、決められた環境で観測できた結果と、意図的な失敗試験を根拠にする。
未実行、環境不足、時間切れ、失敗、合格を分ける。
ログに成功文字列が出ても、必要な処理が実行されなかった場合は不合格とする。

QEMU とファームウェア、CPU と機種、メモリ量、ツールチェーン、ソースのコミット、
試験の入力と終了条件を記録する。起動試験には時間制限と明示的な成功・失敗の通知を設け、
ハングや予期しない再起動を合格にしない。

試験では仮想マシンの画面を開かず、シリアル出力と終了状態を観測する。
ホストの入力操作、生ディスクの割り当て、ホストのホーム共有、通常の外部ネットワーク接続は使わない。
必要な開発用ブリッジは、接続先と用途を限定して別の試験として記録する。

## 実装の依存順序

| 段階 | 前提 | 実装する範囲 | 合格条件 |
| --- | --- | --- | --- |
| M0: 設計と開発環境 | なし | 対象機種、取得元と版、ローダー方針、ビルド分離、試験手順 | 新しい環境でも同じ手順を追える。必要な依存と未決事項を説明できる |
| M1: 起動 | M0 | UEFI からの引き継ぎ、カーネルのログ、例外処理 | Boot Services 終了後のコード実行を確認し、故障時に診断して停止できる |
| M2: メモリと隔離 | M1 | 物理メモリ管理、ページテーブル、ユーザー空間、最小のシステムコールと実行切替 | 不正アクセスを拒否し、無関係なプロセスと OS の基本動作を継続できる |
| M3: 権限とサービス | M2 | IPC、Capability、初期サービス、RAM 上の資料読み取り | 許可した操作が成立し、権限の偽造、流用、失効後の利用を拒否できる |
| M4: 作業管理 | M3 | 操作契約、承認、資源上限、固定応答のテスト用エージェント | 提案から結果確認までを通し、拒否・失敗・中断・成否不明を区別できる |
| M5: 永続化と復旧 | M4 | 制限した仮想ブロックデバイス、操作記録、結果照合、再起動後の復旧 | 途中停止と記録破損を検出し、完了済みの副作用を無条件に繰り返さない |
| M6: ゲスト内の推論 | M4。再起動後の継続には M5 | CPU 推論器、モデル読み込み、資源制限、要約の下書き | ホストの推論を止めてもゲスト内で処理でき、対象外の資料とネットワークへの操作を拒否できる |
| M7: 日常利用と実機 | M5 と M6 | 画面、日本語入力、ネットワーク、更新、実機ドライバーを個別に追加 | 機能ごとの受け入れ試験と復旧試験を満たす。実機は機種別に結果を残す |

マルチコア、GPU 推論、既存アプリ互換性は追加の設計判断とする。
M1 の達成を日常利用できる OS の完成とは扱わず、M4 の模擬応答を AI 推論の実装とは扱わない。
ホスト側のモデルを使うブリッジ実験を行っても、M6 の合格条件は満たさない。

## 各段階の故障試験

| 段階 | 故障を与える方法 | 観測するもの |
| --- | --- | --- |
| M1 | メモリマップのキー不一致、壊れた起動情報、意図的な CPU 例外 | 引き継ぎ失敗の区別、診断ログ、制限時間内の終了 |
| M2 | ユーザープロセスからカーネル領域・他プロセスへアクセス、二重解放、確保枯渇 | 保護違反の捕捉、予約領域の保護、資源の回収 |
| M3 | 無効・古い・別主体のハンドル、失効済み派生権限、過大な IPC | 拒否理由、対象の不変、受け手の継続動作 |
| M4 | 不正な操作形式、承認後の対象変更、無限ループ、応答喪失 | 承認の結び付き、予算の強制、成否不明の状態 |
| M5 | 副作用と記録の各境界で停止、切り詰めた記録、満杯の保存領域 | 再起動後の照合、重複防止、回復不能の明示 |
| M6 | 破損したモデル、過大な入力、資料中の悪意ある指示、推論プロセスの強制終了 | 読み込み拒否、制限、権限外の操作拒否、手動操作の継続 |
| M7 | 更新の途中停止、旧版への復帰、ドライバー停止 | 起動可能性、データ形式の互換性、回復手順 |

拒否だけで試験を満たさないよう、各権限試験には対応する正常系を置く。
承認された操作が一度成立すること、拒否された操作で対象が変わらないことを両方確認する。
権限検査を意図的に破るテスト用構成でも同じ試験を行い、試験が異常を検出できることを確かめる。
その構成は試験専用とし、通常のビルドへ混入しない条件も確認する。

## 最初の実装単位

M0 と M1 の境界までを、最初の小さな実装単位にする。

- 新しいコードの配置と、既存の Bun / Python / Tauri ビルドからの分離を確定する。
- Rust、リンカー、UEFI ファームウェア、ローダー、QEMU の依存とライセンスを確認する。
- カーネルへの起動情報を定義し、最小のシリアルログと失敗処理を作る。
- ヘッドレス起動の試験を用意し、正常起動と意図的な失敗の結果を分ける。
- 成功と失敗の記録を確認してから、メモリ管理とユーザー空間へ進む。

必要な環境がない場合は、足りないツールと導入範囲を特定する。
依存の導入や起動設定の変更について、既存の設定に影響する範囲を明示する。
この設計文書の追加自体は、インストール、実機起動設定、カーネルのビルドを実行しない。

## 文書変更の検証

この文書群の変更では、[Git ワークフロー](../GIT_WORKFLOW.md)の文書向けチェックに従う。

```powershell
bun run check:encoding
bun run check:git-hygiene
git diff --check
```

新規ファイルも検査対象に含まれていることを確認し、相対リンク、設計の責務、
段階の前提、未検証の表現を照合する。カーネルの起動試験やアプリの動作試験を、
文書検査の結果から合格と推定しない。

## 証拠と成果物

検証結果には、対象のコミット、固定した環境、実行した試験、期待値、実際の結果を残す。
標準出力に秘密情報や私的な資料を含めず、必要な診断だけを扱う。
ベンチマークは入力と資源条件を固定し、起動時間、応答時間、使用メモリを実測してから記載する。

ローカル検証用のカーネルや仮想ディスクは、実装段階で用途を限定して扱う。
配布用の EXE、インストーラー、ZIP、リリースフォルダー、配布用チェックサムは、
明示的な許可がない限り生成しない。PR は設計やソースをレビューする単位とし、公開や merge を自動で行わない。
