# サイズ別予算の起動への適用と拒否

2026-09-27、固定12形状のサイズ別推論へ、検査済みのarena予算を適用する経路を追加した。
前段の実験で解析式が実測値と一致したため、今回は解析式を採用する。回帰モデルは比較用の提案器として維持する。

## 処理の流れ

1. ホストのrunnerが専用推論ELFをビルドし、実際のファイルからSHA-256を計算する。
2. 起動モード・形状・ページ予算・ELF識別値・測定単位を持つ240 bytesの予算表を生成する。
3. 予算表と、信頼側のELF識別値を別々にカーネルへ組み込む。
4. カーネルは長さ、形式版、単位、件数、予約領域、ELF識別値、全行の順序・形状・予算を検査する。
5. 検証済みの型だけが `ReadAgent` のページ上限へ反映できる。Agentへのバインドとプロセス構築は同じ予算から起動設定を得る。

対象はビルド時に組み込む実験用の予算表である。実行中のLLMからの要求、任意モデルのロード、一般アプリの動的起動は追加していない。

## 守る制約

- 測定単位はnative arena pagesのみ。Pythonの追跡対象bytesやホストRSSの値を受け付けない。
- 形状は信頼側の固定表と完全一致させてからサイズ計算する。未検査の整数を乗算しない。
- 各予算は1〜16ページで、既知の配置に必要なページ数以上でなければならない。
- CPU上限1024 tick、プロセスの総フレーム上限32、通信・資料権限、操作承認の方針を変更しない。
- 既定の `--budget-recovery off` では、不正な表を永続journalの処理・Agentへの権限発行・ユーザープロセス起動より前に拒否する。
- 検査を通るまで不足予算を黙って16ページへ拡大しない。

`fixed` は従来どおり全形状へ16ページを与える明示的な試験設定。
`analytic` は各形状へ解析式の必要量を与える。不正な表から `fixed` へ自動的に切り替える処理ではない。

明示的な別試験 `--budget-recovery retry` では、全行を検査した後の選択行の予算不足に限って、Agent記録と一度だけの起動再試行へ接続する。
[記録・復旧の契約](AGENT_BUDGET_RECOVERY_VALIDATION.md) を参照。形式異常や上限違反は補正しない。

## 予算表の形式

全数値はlittle endian。ELF識別値は32 bytesのSHA-256。

| オフセット | 内容 |
| --- | --- |
| 0 | 4 bytesのmagic `EAB1` |
| 4 | u16形式・配置版=1 |
| 6 | u16単位=1（native arena pages） |
| 8 | u32行数=12 |
| 12 | u32予約領域=0 |
| 16 | 専用推論ELFのSHA-256、32 bytes |
| 48以降 | 16 bytesの行を12件：u32起動モード、u16 batch/features/classes/pages、u32予約領域=0 |

行は起動モード75〜86の順序とし、重複・欠落・未知の形状を拒否する。
配置版1の解析式は、i32入力、i32重み、8 bytes整列したi64出力の合計を4 KiB単位へ切り上げるもの。
この構成や推論ELFを変更する場合は、形状・必要量・識別情報を再検証する。

SHA-256は信頼するホストのビルド工程で取得する。カーネルは予算表の識別値をその値と照合する。
カーネル自身によるELF全体の再ハッシュ、署名検証、Secure Bootを追加したわけではない。
ビルド環境やカーネルを改変できる相手からの保護を、この照合だけで保証するものではない。

## QEMUの結果

Windows上の固定QEMU 11.1.0 / q35 / TCG / 1 CPU / 256 MiB、Rust 1.96.0で23ケースが合格した。

| 群 | 件数 | 確認内容 |
| --- | ---: | --- |
| 解析式の予算を適用 | 12 | 2/2/5/6/10/11/3/8/2/5/10/13ページの上限で計算を完了し、終了後に全フレームを回収 |
| 不正な提案を拒否 | 7 | 形式版、単位、ELF識別値、形状、上限超過、予算不足、切り詰めをそれぞれ起動前に拒否 |
| 既存動作の回帰 | 4 | fixedでのサイズ0、縮小予算での承認、割り当て拒否、CPU予算超過 |

成功ケースでは計算結果のchecksum、予算適用が権限発行より先に行われること、arenaの上限・割り当て・回収、journalの不変を検査した。
不正提案のケースでは、終了コード61と正確な拒否理由を要求し、Agent・プロセス・永続journal処理へ進んだログを不合格にする。
不正提案の試験にはjournalディスクを接続しない。通常の成功ケースは専用ディスクを接続し、全体の不変を検査する。

前回の評価4形状では、実際の起動上限が次のようになった。

| 形状 (batch, features, classes) | 従来上限 | 適用した上限 | 実際の割り当てピーク |
| --- | ---: | ---: | ---: |
| (2,128,8) | 16 | 2 | 2 |
| (3,256,16) | 16 | 5 | 5 |
| (2,384,24) | 16 | 10 | 10 |
| (8,384,24) | 16 | 13 | 13 |

小さくなったのは許可する上限。元の計算も必要なページだけを確保していたため、この結果を実使用メモリの削減や高速化とは扱わない。
全104種類の既存試験を再実行したわけではない。

## 再現と記録

```powershell
python native-os/tools/validate_arena_budget.py --output native-os/out/arena-budget-new --qemu <qemu-system-x86_64.exe> --firmware-dir <share>
```

収集先は新規ディレクトリに限る。今回の記録は `native-os/out/arena-budget-20260927/summary.json` と各群のreport・serialログ・起動情報・予算表・期待ELF識別値。
既存の通常runnerの出力は各試験で更新されるが、検証用ディレクトリには各群のコピーを保存する。
ケースのserialと予算表のSHA-256を結果と照合した。これは署名されていないローカルの実行記録である。

単独で実行する場合：

```powershell
python native-os/tools/boot_test.py --case infer-size-11 --arena-budget analytic --qemu <qemu-system-x86_64.exe> --firmware-dir <share>
python native-os/tools/boot_test.py --case infer-size-0 --arena-budget insufficient --qemu <qemu-system-x86_64.exe> --firmware-dir <share>
```

負例指定は `infer-size-0` に限定する。通常の計測CLIや既存の `native_sized.py` は既定の `fixed` を使い、従来の16ページでの評価を維持する。

Rust単体試験82件、Python判定器55件、研究用試験24件が合格した。
Pythonの両試験群はWindowsとUbuntuで確認し、同じ専用ELFから生成した解析式の予算表がバイト単位で一致することも確認した。
QEMU自体はWindows側で実行している。Clippy（ホストlib・ゲストkernel、警告をエラー化）、Rustfmt、変更したPythonのRuffも合格した。

## 残る段階

任意の学習済みモデルや入力から必要量を推定し、不足時に再計画して再起動する処理は未実装。
固定負荷については、拒否・再計画・起動予約・完了をAgentの専用記録へ結び付け、一度だけ起動を再試行する処理を追加した。
実装済みの範囲と再起動時の制約は [Agentの予算拒否記録と起動再試行](AGENT_BUDGET_RECOVERY_VALIDATION.md) を参照。
動的な一時バッファや複数Agentの競合を含む負荷への一般化も、別の測定と検証が必要になる。
