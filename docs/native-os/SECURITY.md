# 独自 OS の権限と信頼境界

状態: 設計要件。安全性、形式検証、完全な隔離を達成したという報告ではない。
[既存の脅威モデル](../THREAT_MODEL.md)のローカルファーストと操作確認の方針を引き継ぎ、
独自カーネルで必要になる強制の仕組みを定める。

M2b の実装で確認した境界と未対応事項は [ユーザー空間の検証](USERSPACE_VALIDATION.md) を参照する。
以下の Capability・資源制御・復旧の要件は、M2b で達成したものではない。

## 信頼するものと検証するもの

信頼の中核には、CPU の保護機能、起動経路、カーネル、最小限の初期サービスを置く。
各サービスは、自分が所有する資源について信頼境界を持つ。
カーネルの侵害、悪意あるファームウェア、物理攻撃、未対策の DMA、サイドチャネルまでを
初期実装で防げるとは扱わない。対象デバイスの追加時に脅威モデルを更新する。

ユーザーの依頼、モデル出力、モデルファイル、検索結果、取得文書、外部応答は、
それぞれ入力として検証する。AI の出力に管理者の指示らしい文章があっても、権限は増えない。
操作を実行するサービスは、作業管理から来た依頼も対象と権限について検証する。

## Capability の基本要件

Capability は、特定の資源に対する操作権を表す。seL4 の説明する、偽造できない資源への参照を
設計の参考にする。seL4 を採用したり、その検証結果をこの OS が引き継いだりする意味ではない。
[seL4 の公式解説](https://docs.sel4.systems/Tutorials/capabilities.html)

初期案では、カーネルがプロセスごとのハンドル表を所有し、利用者に内部ポインターを渡さない。
オブジェクト ID、世代、権利、保有主体を照合し、無効な値は拒否する。
ハンドルの数値を別のプロセスへコピーしても権限を得られない。
別プロセスへの委譲は専用の検証経路を通す。

| 操作 | 要件 |
| --- | --- |
| 付与 | 信頼された権限管理者が、対象、権利、受領者を指定する |
| 委譲 | 元の権限以下に限定し、再委譲の可否を管理する |
| 利用 | 呼び出し元、対象、権利、失効状態を利用時に検証する |
| 失効 | 派生した権限にも反映し、古いハンドルの再利用を拒否する |
| 終了 | プロセス終了時にハンドルと予約資源を回収する |
| 再起動 | 以前のハンドルをそのまま有効化しない |

カーネルは、アドレス空間、IPC エンドポイント、デバイス等の権限を強制する。
ファイル名、文書の版、外部送信先などの意味は、資源を所有するサービスが強制する。
特権サービスが依頼元以上の権限で代理実行してしまう問題を防ぐため、
依頼元と委譲範囲を呼び出しごとに結び付ける。

ファイル操作では、文字列のパスを検査したあとで別の対象へ解決されないようにする。
対象を確定したハンドルと必要な版情報で操作し、リンクの差し替えや変更との競合を検証する。
失効と操作開始の境界を定め、新たな操作は失効後に拒否する。
既に外部で成立した副作用は、失効によって取り消されたと報告しない。

## 承認と AI 出力

承認は、操作、入力、対象、送信先、期限、適用回数へ結び付ける。
信頼された手動の経路で記録し、AI 自身が承認記録を作れないようにする。
入力や対象の版が変わったら、過去の承認を流用しない。

初期方針では、削除、上書き、外部送信、認証情報の変更、管理操作は個別承認を必要とする。
読み取りも任意のファイルへ広げず、あらかじめ選ばれた範囲に限定する。

モデルの回答をシェル文字列として実行しない。許可された操作の形式へ変換し、
型、長さ、対象、権限を検証する。検索結果や取得文書は参考データとして扱い、
ポリシー、承認、接続先を変更する命令には使わない。

## 情報の保存と外部通信

- 初期の推論プロセスにはネットワーク権限を渡さない。
- 外部接続は専用サービスで管理し、接続先、リダイレクト、名前解決後の宛先を検証する。
- 検索時にも現在の閲覧権限を確認し、派生した索引や要約へ元データの制約を引き継ぐ。
- 記憶の削除は、原文、索引、キャッシュ、要約を対象にする。バックアップの扱いを明示する。
- 認証情報、私的な文書、プロンプト本文、モデル出力全文を標準の監査記録へ保存しない。
- 暗号化は保存中のデータを守る手段と位置付ける。復号後の漏洩を防ぐにはアクセス制御も必要になる。

## 資源制限と停止

M2c の実装は、固定 QEMU・1 CPU・2 プロセスに限り、PIT 割り込みによる切替と累積 tick 上限を扱う。
停止後はカーネル root へ移り、プロセス所有フレームを消去して返却する。
厳密な CPU 時間課金、IPC・I/O の制限、一般的なサービス再起動ポリシーは未実装。
確認済みの条件は [資源回収と実行制御](LIFECYCLE_VALIDATION.md) に記録する。

推論とサービスごとに、CPU 時間、メモリ、IPC の大きさと保留件数、入出力量を制限する。
壁時計の変更で期限を延ばせないようにし、資源の回収処理にも上限を設ける。
手動の停止経路は AI の応答を待たず利用できるようにする。

例外を起こしたプロセスを終了しても、OS の基本操作と無関係なプロセスは継続できることを検証する。
再起動は回数と待ち時間を制限する。障害を繰り返すサービスには権限を無条件に再配布しない。

## 記録と結果の照合

監査記録には、作業 ID、操作 ID、主体の識別子、対象の不透明な識別子、
承認の参照、結果の種類、時刻を必要最小限で残す。
低エントロピーの個人情報を単にハッシュ化して匿名と扱わない。

保存領域が満杯のときの動作を決め、監査が必須の変更操作は記録できなければ開始しない。
読み取りや手動復旧まで停止させるかは別に定める。
ハッシュの連鎖は改変を検出する補助にはなるが、信頼された終端がなければ
履歴全体の置換やカーネル侵害を防げる証拠にはならない。

実行したサービスの応答と、必要なら資源の状態を照合して結果を確定する。
モデルが「完了した」と出力しただけでは成功にしない。

## 必須の拒否試験

| 入力・障害 | 期待する結果 |
| --- | --- |
| 無効なハンドル、他プロセスの数値のコピー | 拒否し、対象を変更しない |
| 親権限の失効後に派生権限を使う | 失効を確認して拒否する |
| 承認後に入力、対象の版、送信先を変更する | 再検証と再承認を要求する |
| 文書に権限昇格や外部送信の指示を混ぜる | 取得データでは権限が増えず、操作を拒否する |
| IPC の洪水、メモリ枯渇、無限ループ | 上限を適用し、基本操作を継続する |
| 副作用の直後にプロセスが停止する | 成否不明を記録し、無条件に再実行しない |
| 結果記録の破損、記録領域の枯渇 | 成功を捏造せず、照合または明示的な失敗へ進む |

細かな試験の依存順序と証拠の残し方は、[検証計画](MILESTONES.md)に定める。
