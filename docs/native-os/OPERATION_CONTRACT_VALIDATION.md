# M4a：操作契約と RAM 上の承認・記録

## 今回の範囲

起動定義（PR #122）を土台に、資料0の読み取り1操作を承認・実行・結果記録へ通す。
固定応答のクライアント ELF と資料サービス ELF が Ring 3 で既存 IPC を使う。
AI 推論、人が使う承認画面、外部 API、保存デバイス、再起動後の記録復旧は含まない。

承認元は QEMU 試験専用の信頼済み入力である。クライアントが送った提案をそのまま承認せず、
カーネル内の独立した期待値と完全一致した場合だけ、許可または拒否を入力する。
ゲストから承認元を設定する API はない。opcode 14 の自己承認要求は拒否する。
この試験を、実ユーザーが対話的に承認したことの証明とは扱わない。

## 契約と境界

`operations::Plan` は操作 ID、実際の依頼元、実行サービス、形式の版、資料権限ハンドル、
読み取り範囲、バイト予算、期限を保持する。操作種別は読み取りに固定する。
資料は不変の RAM データであり、可変資料の版管理は未実装。

提案・承認・実行開始で値を照合する。IPC の送信者はカーネルが確定し、要求中の自己申告を使わない。
資料の所有者と世代は既存 Grant 検査を通す。操作ケースでは旧来の直接読み取り opcode 1 も受け付けず、
承認経路を迂回できない。CPU・メモリ上限は BOOT 定義で維持し、操作は最大16 bytes と
カーネルの単調 tick 1024 を期限とする。tick は実時間の厳密な課金ではない。

状態は Proposed → Approved → Running → Completed。
拒否は Denied、実行前の中断は Interrupted、確定した読み取り失敗は Failed、
実行中のサービス停止で結果を確定できない場合は Unknown として区別する。
Completed は読み取り処理の完了を意味し、一般的な外部副作用や受信者への配達完了は保証しない。

記録は RAM 上の最大8イベントと、保存した完全な操作契約で構成する。
イベントには操作 ID・状態・カーネル tick を含め、本文のバイトは含めない。
完了を記録する空きを実行前に確保できなければ実行しない。
同一セッションは1操作だけを保持し、完了・失敗・中断・成否不明からの再実行を認めない。
拒否された API 呼び出しすべての恒久的な監査ログを実装したものではない。

## 起動試験

| ケース | 確認する結果 |
| --- | --- |
| operation-complete | 未承認実行と自己承認を拒否。入力変更を拒否。16 bytes を1回だけ返し、二重実行を拒否 |
| operation-denied | 信頼済み入力が拒否。実行回数0、状態 Denied |
| operation-interrupted | 承認後・実行前に取り消し。実行回数0、状態 Interrupted |
| operation-unknown | 実行開始後にサービスが実際に無効命令で停止。クライアントは EPIPE を受け取り、状態 Unknown。自動再実行なし |
| operation-failed | 承認した範囲が資料の範囲外。状態 Failed、再実行を拒否 |

各ケースはクライアントの正常終了、サービスの終了または指定した故障、全フレーム・通信・資料権限の回収を確認する。
判定器は記録の順序、実行回数、自己承認拒否、故障証拠、確保数の復元を照合する。
永続化は M5 で、記録と対象の更新の整合性、途中停止、記録破損、成否不明の照合を別途実装する。

## 検証環境と記録

2026-09-20、Windows / Rust 1.96.0 / 固定 QEMU 11.1.0 / 既存 UEFI。
既存の `DEPENDENCIES.md` の取得・点検済み環境を再利用し、新規依存は導入していない。
ソースと build script、依存、hooks、CI、バイナリの入力、認証・通信経路の変更を確認した。
CI・hooks・認証情報の扱い・外部通信は変更せず、ゲスト NIC・実ディスク・ホスト共有は使わない。

最終版の結果：QEMU 50/50、Rust 57/57（11 + 39 + 7）、Python 判定器 27/27。
Rustfmt、ホスト・x86_64-unknown-none の Clippy（警告をエラー扱い）、差分検査、staged Gitleaks が成功。
承認済み契約の照合を一時的に無効にする負の対照試験では operation-complete が期待どおり失敗した。
元のソースをバイト単位で復元し、同ケースの成功を再確認した。無効化したコードはコミットに含めない。
ローカル結果は ignored の native-os/out/ に保存する。CI の結果は PR 上で別に確認する。

## 回帰試験で見つかった順序依存

初回の全体試験では ipc-deadlock が失敗した。最初のタイマー割込みで PID 1 が先に待機し、
PID 0 が正しく EDEADLK を受けたが、試験用プログラムが逆の順序しか認めていなかった。
両プロセスで同じ受信結果の処理を使い、拒否された側が相手を起こす形に修正した。
判定器はどちらの順序でも「1件のデッドロック拒否と反対側の起床」を要求する。
同じ PID を起こす偽の記録は拒否する。カーネルのデッドロック検出条件は変更していない。
